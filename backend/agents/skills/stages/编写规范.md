# stages 阶段技能（SKILL.md）编写规范

阶段技能是分析工作流的**判断面**：SKILL.md 定义「怎么判断」，执行层负责「取数据、跑 LLM、写回 state」。新增一个分析阶段或定性子块 = 新增一个 SKILL.md 文件，**零代码扩展**。

> **P4 现状（2026-08-15）**：原 Python 侧工厂 `stage_tools.py::_load_stages()` 已在 P4 退役，方法论资产同步迁移至 `.dsh/skills/`（DSH 侧由 `.dsh/plugins/invest-five-stage/prepare.ts` 的 `scanBlocks` 扫描加载）。本仓库 `backend/agents/skills/stages/` 保留的 SKILL.md 为 Python 侧方法论原文，由 `analysis_chain.py` 直读（如 `run_reverse_checklist`），frontmatter 与目录结构经 `tests/test_agents/test_skill_load.py` 校验。

- 生效入口：方法论资产已迁 `.dsh/skills/`（DSH 侧 `.dsh/plugins/invest-five-stage/prepare.ts` 的 `scanBlocks` 扫描加载）；本仓库 `backend/agents/skills/stages/` 为 Python 侧方法论原文，由 `analysis_chain.py` 直读（如 `run_reverse_checklist`），frontmatter 经 `tests/test_agents/test_skill_load.py` 校验
- 关联设计：`docs/superpowers/specs/2026-08-13-analysis-workflow-5stage-skill-design.md`、`docs/superpowers/specs/2026-08-13-openharness-embed-design.md`（十九节）
- 方法论来源：`docs/股票WEB监控系统/投资分析框架.md`（八项原则 / 信号灯 / 逆向清单）

## 目录布局

```
backend/agents/skills/
  ├── investment-framework/SKILL.md        # 主 skill：角色 + 5 阶段骨架 + 顺序/依赖 + 八项原则 + 评级纪律
  └── stages/                              # 分析阶段容器（本规范作用域）
      ├── <stage>/SKILL.md                 # 阶段技能（会被工厂扫描生成工具）
      └── <stage>/blocks/<block>/SKILL.md  # 阶段内子块（可选，随阶段目录内聚）
```

- 阶段目录名建议用 `kebab-case`（如 `reverse-checklist`）；frontmatter 的 `name` 用 `snake_case`（如 `run_reverse_checklist`）。
- `stages/` 根下的普通 markdown 文件（如本规范）不会被当作技能加载，可放心放置说明文档。
- 阶段内子块**不注册进 skill registry**，由 `StageTool` 工厂构造时扫描 `blocks/` 加载。

## Front Matter 字段

技能文件以 **Markdown + Front Matter** 编写，`---` 包裹 YAML 头部，正文为 markdown。

### Stage 级字段

| 字段 | 必填 | 类型 | 说明 |
|:--|:--|:--|:--|
| `name` | 是 | string | 工具名（自动生成 `StageTool.name`），唯一，`snake_case` |
| `description` | 否 | string | 技能描述，注入系统提示的 Available Skills 列表，供 LLM 按需用 `skill()` 读取 |
| `type` | 否 | string | 执行类型：`qualitative`（默认）/ `hybrid` / `readonly` |
| `output_field` | 否 | string | 写回 state 的顶层键（`state.<output_field>`），默认取 `name` |
| `order` | 否 | int | 阶段执行顺序，全表唯一递增（当前 2-5），默认 99 |
| `depends_on` | 否 | list | 需要注入的 state 字段名数组，执行时按此注入数据 |
| `blocks_dir` | 否 | string | 阶段内子块目录名（相对 stage 目录，如 `blocks`）；有则遍历子块 |
| `version` | 否 | string | 版本号（自由元数据，代码不解析） |
| `tags` | 否 | list | 标签（自由元数据，代码不解析） |

> 字段语义与代码契约：frontmatter 加载只读取上表必填字段，`version`/`tags` 仅作文档性元数据；未知字段被忽略，不会报错（必填字段存在性由 `tests/test_agents/test_skill_load.py` 校验）。

### Block 级字段（`blocks/<block>/SKILL.md`）

| 字段 | 必填 | 类型 | 说明 |
|:--|:--|:--|:--|
| `output_field` | 是 | string | 写回 `qualitative_analysis.<output_field>` 的键，同时写兼容顶层字段 |
| `name` | 否 | string | 子块名，默认取目录名 |
| `title` | 否 | string | 前端展示中文标题（如「商业模式」），默认取目录名 |
| `order` | 否 | int | 子块执行顺序（升序），默认 99 |
| `handler` | 否 | string | 专用处理函数名（如 `dedicated_operating_quality`）；含确定性逻辑时声明，工厂走专用分支而非通用 LLM |

## 正文结构

正文以 `[NO_COMPRESS_START]` 开头、`[NO_COMPRESS_END]` 结尾，包裹「请勿压缩」的方法论内容。这是重要内容约定——代码按原样注入，标记本身不参与解析，但明确告知任何上下文压缩逻辑不得省略中间内容。

```markdown
[NO_COMPRESS_START]
以下内容为本技能核心方法论，非常重要，请不要进行压缩。

# 技能名称

开头一段：用一两句说明本阶段在整体工作流中的位置与目标。

## 技能提示词
核心职责和工作原则（LLM 的角色、立场、数据口径）。

## 任务描述
定义能力范围与目标：做什么、不做什么、最终产出。

## 处理流程
完成任务的具体流程步骤，可含分组问题清单。

## 工具说明
可以使用的工具和技能及其使用方式（本阶段需要哪些工具/前序结论）。

## 输入来源
执行时需要的输入——本系统为按 `depends_on` 注入的 state 字段（非文件路径），逐字段列出含义。

## 引用规则
执行中必须遵守的规则和限制（框架约束、口径、证伪原则等）。

## 输出格式
执行完成后输出的 JSON 结构（写入 `state.<output_field>`），给出字段与取值说明。

## 全局约束
执行时必须遵守的全局红线（否决触发、禁止行为、硬性纪律）。

## 示例
一个输入→输出的完整示例，帮助 LLM 对齐产出形态。

[NO_COMPRESS_END]
```

各节的定位（适配本系统，非通用 skill 模板）：

- **技能提示词**：注入 LLM 时即被读取，应直接写「你是 X」与核心原则，不用绕弯。
- **输入来源**：本系统输入来自 state（`depends_on` 注入），不是文件路径；逐字段列出字段名与含义。
- **输出格式**：必须给 JSON schema。stage 级 `qualitative` 返回结构化对象；带 `blocks_dir` 的子块返回 `{"text": "..."}`（100-200 字结论）。
- **引用规则 / 全局约束**：区分「方法论软约束」与「硬性纪律」。否决类规则（如 `checklist_veto`）放全局约束，确保语义最强。
- **示例**：放一个真实感输入→输出，比多段描述更能约束产出形态。

## 执行语义（代码契约）

> 本节描述的是 P4 退役前的 Python 工厂（`stage_tools.py` 的 `StageTool` / `_run_qualitative` / `harness_output`）历史契约，保留作方法论参考。P4 现状：DSH 侧由 `prepare.ts scanBlocks` 扫描 `.dsh/skills/`，Python 侧仅 `analysis_chain.py` 直读阶段 SKILL.md（逆向清单 / 结论两阶段仍保留专用分支）。

工厂扫描 `stages/`，为每个 stage skill 生成一个 `StageTool`，按 `type` 分发执行：

| type | 行为 |
|:--|:--|
| `qualitative` | 有 `blocks_dir` → 遍历子块，每子块一次 LLM 调用并写 `stage_results.<stage>.<output_field>`；无 `blocks_dir` → 单次 LLM 定性 |
| `hybrid` | LLM 输出半结构化结果（如击球 PE 区间）→ 内部引导确定性工具完成定量，合并写回 |
| `readonly` | 不产出写回（基本数据阶段由 `read_context` 专用只读工具覆盖，不生成 stage 工具） |

- 子块 frontmatter 含 `handler: dedicated_*` 时，走注册表 `_HANDLERS` 中的专用处理函数（确定性检查 + LLM 定性），不经过通用 LLM 分支。
- `run_reverse_checklist`、`output_conclusion` 两个阶段在 `_run_qualitative` 中有**专用代码分支**（`analysis_chain.run_reverse_checklist` / `harness_output.validate_output_shape` + `apply_veto`）。两者的 **SKILL.md 正文都直接驱动 LLM**：逆向分支把 `stage.skill_content` 作为 prompt 主文注入（14 问 / 输出格式 / 全局约束，另附 `_inject` 注入的 depends_on 数据），结论分支同样以 `stage.skill_content` 拼装 prompt，并在输出后做否决与形状校验兜底。改 SKILL.md 即改行为，无需改代码。
- 执行后所有结果写入 `state.stage_results.<stage>`（`_merge` 深合并，多阶段不互相覆盖），并同步写 `state.<output_field>` 兼容既有消费方。

## 扩展边界

| 扩展类型 | 零代码 | 做法 |
|:--|:--|:--|
| 新增纯 LLM 判断阶段 | 是 | `stages/<xx>/SKILL.md` 一个文件 |
| 新增定性子块 | 是 | `stages/<stage>/blocks/<xx>/SKILL.md` 一个文件 |
| 调整阶段顺序/依赖/判断指导 | 是 | 改主 skill / stage skill / block skill 文本 |
| 需要新数据字段 | 否 | 数据采集 + 注入映射需改代码（数据面） |
| 需要新算术公式 | 否 | 需新增确定性工具类（计算面） |
| 新增 `dedicated_*` 专用 handler | 否 | 需在 `_HANDLERS` 注册处理函数（计算面） |

## 编写检查清单

- [ ] frontmatter 用 `---` 包裹、`name`（stage）/`output_field`（block）必填
- [ ] `order` 全表唯一且升序衔接既有阶段；新增子块 `order` 不与现有子块冲突
- [ ] `depends_on` 列出的字段真实存在于 state（`_inject` 会按此注入）
- [ ] `output_field` 与 state 键一致，避免写回错位
- [ ] `blocks_dir` 值 = stage 目录下的子目录名，且子目录内每个 `SKILL.md` 都有 `output_field`
- [ ] 正文用 `[NO_COMPRESS_START]` / `[NO_COMPRESS_END]` 包裹
- [ ] 按模板补齐 9 节（技能提示词/任务描述/处理流程/工具说明/输入来源/引用规则/输出格式/全局约束/示例），「输入来源」列 state 字段而非文件路径
- [ ] 「输出格式」给出 JSON schema，与 `validate_output_shape` 或下游消费键一致
- [ ] 涉及否决/硬纪律的规则写入「全局约束」
- [ ] 运行 `pytest tests/test_agents/test_skill_load.py` 验证新阶段/子块 frontmatter 与目录结构被正确加载（DSH 侧另跑 `.dsh/plugins/invest-five-stage` 的 vitest 验证 `prepare.ts scanBlocks`）
